# 语法讨论书

本文件记录 mio 在「TypeScript 语法之上建立静态强类型语义」过程中的语法与语义决策。
凡涉及**新增类型、新增语义规则、新增后端形态**的讨论，均在此登记结论。
本文件只写**已决结论**与**准入标准**，不写探索过程。

TaolunID 追溯见 `docs/Taolun.md`。本文件为**唯一权威**，`AGENTS.md` 与 `README.md` 中与之冲突的表述以本文件为准。

---

## 一、目标与定位

### 1.1 一句话目标

> **让 TypeScript 直接编译成本机机器码执行。类型参与代码生成，内存布局在编译期确定，全程没有 JavaScript 引擎。**

### 1.2 要解决的问题

TypeScript 的性能天花板不在 TypeScript，在 JavaScript 的值模型。
只要对象布局要等到运行时才知道（动态属性、原型链、装箱），编译器就无法生成好的机器码。这不是优化问题，是语义问题。

现有方案各有取舍：

| 方案 | 症结 |
|---|---|
| `tsc` + Node / Bun / Deno | 类型全擦除，跑的是 JS 语义 |
| Static Hermes | 仍是 JS 语义 + 类型特化，类型只用来加速 JS 执行路径 |
| AssemblyScript | 类型真的参与代码生成 ✅，但要求改写法、手动内存、生态断裂、存在不检查的 `unchecked()` |
| **mio 目标** | 类型真的参与代码生成 + 不改写法 + 自动内存 + 内存安全 |

### 1.3 形态定性

不造新语言，做的是**同一套 TypeScript 语法的第二套语义实现**。语言 = 语法 + 语义，TS 给了语法，语义需要自己定义。

| 层 | 决策 |
|---|---|
| 词法 | 不改。继续用 OXC parser |
| 语法 | 不加关键字、不加新语法形式。新增类型名通过内置 `.d.ts` 声明，parser 视为普通类型引用 |
| 类型系统 | 是 TypeScript 的超集：既有类型保留，另加机器类型与结构类型 |
| 运行时语义 | 自己定义。这是本文件主要内容 |
| 执行形态 | **AOT 编译为本机机器码可执行文件** |

由此得出两条硬约束：

1. **任何新能力都必须是「新类型名 + 新语义」，不能是「新语法形式」**。加语法等于自绝于编辑器、`.d.ts` 与 OXC parser。
2. **语法层加得越多、语义层跟不上，就是谎报能力**（对齐 AGENTS.md 的「预留字段必须告警」规则）。

静态语言的丰富度 90% 来自类型系统与值模型，不到 10% 来自语法关键字。目标是**语义全**，不是语法全。

## 二、总体架构

```
TS 源码 (.ts)
   │
   │  OXC parser
   ▼
AST
   │
   │  语义层：TypeRegistry + 表示决策表 + 健全性检查
   ▼
IR（已带表示标注：I32Add / LoadField(offset=8) / Call(conv=sysv)）
   │
   │  代码生成器
   ▼
本机机器码（ELF / Mach-O 可执行文件）
   │
   ▼
操作系统直接加载执行
```

**没有 wasm，没有 JS 引擎，没有解释器中间层。** 输出是普通原生可执行文件。

### 2.1 后端：Cranelift

| 方案 | 编译速度 | 优化质量 | 依赖 | 结论 |
|---|---|---|---|---|
| **Cranelift** | 极快 | 中高（对标 -O1~-O2） | 纯 Rust | ✅ **采用** |
| LLVM | 慢 | 最高 | C++ 大依赖 | 后期可选替换 |
| 自研 codegen | 缓慢 | 初期很低 | 无 | 不采用 |

采用 Cranelift 的理由：

- 纯 Rust，无 C++ 工具链依赖
- 编译速度快到可作为 REPL 后端
- 自带寄存器分配、指令选择、基本优化，本层只需写「IR → Cranelift IR」的机械映射
- 由 Wasmtime 工业验证

「不需要自己写寄存器分配与指令选择」是本架构的核心杠杆——这是编译器最难的部分。

### 2.2 字节码 VM 的地位

字节码 VM 仅为开发期脚手架（便于调试、快速迭代语义），**不是交付形态**。若与 Cranelift 后端产生维护冲突，可直接砍掉。

### 2.3 wasm 的地位

wasm 是**可选第二目标**（「能编译成 wasm 给浏览器跑」），与主路径共享同一套 IR 与表示决策表。不是性能主路径，不参与主线验收。

### 2.4 Boa 的地位

Boa 是阶段 A 的既有执行后端，**不在阶段 B 主路径内**。
「静态区 / 动态区双区共存」降级为**可选互操作能力**，用于渐进迁移与 `node_modules` 生态桥接，不作为核心机制。

`@std/*` 的核心逻辑本就以纯 Rust 实现，跨阶段复用；只需替换最外层绑定层（Boa 绑定 → 原生 ABI）。

## 三、借鉴来源：按能力拆开借

| 来源 | 借什么 | 理由 |
|---|---|---|
| AssemblyScript | 机器类型全集、数值字面量规则、溢出回绕语义、泛型单态化、内存布局 | 唯一解过「TS 语法 → 原生语义」映射的现成 oracle |
| C# | `struct` 与 `class` 的值/引用语义分野、`readonly`、`in`/`ref` | 该分野是 Java 与 JS 都缺、而静态运行时的第一性地基 |
| Rust | `enum` + `match` 的代数数据类型、`Option<T>` 式可空性、**健全性优先** | tagged union 是后端最好实现的形态；健全性是安全承诺的地基 |
| Cranelift | 代码生成后端 | 见 2.1 |
| Java | 仅作反面教材：`null`、擦除泛型、装箱 | 三个都是静态运行时的性能与正确性陷阱 |
| TypeScript | 语法一个字符都不加 | 见 1.3 |

与 AssemblyScript 的两处关键分化：

1. **健全性**：不提供 `unchecked()` 式的无检查类型转换。类型断言必须可审计。
2. **自动内存**：默认 GC，用户不需要想内存。

这两条即 mio 的差异化定位——AssemblyScript 占了「类型参与代码生成」但不要健全性与自动内存。

**暂不借鉴**：Rust 的借用检查（`&mut` 独占）。它是好设计，但要求后端围绕生命周期整体设计，在值模型稳定前引入会阻塞阶段 0。值模型与 GC 稳定后再议。

## 四、特性准入标准（三问）

任何新特性（`struct`、泛型、闭包、可空性……）进入语言前，必须先答完三问。**答不全则不进入。**

1. **它的内存表示是什么？**
   给不出确切的字节布局 → 该特性不进静态区。
2. **它与宿主 / 外部边界的交互怎么过？**
   过不去，或过的时候需要深拷贝整个对象图 → 太重，不进。
3. **判不出表示时怎么办？**
   只允许两种答案：**编译期报错**，或**显式装箱**。
   禁止偷偷装箱——装箱点必须可枚举、可被 `--show-boxing` 打印。

按此筛：`int32`、`struct`、`enum`/`match`、定长数组、泛型单态化全部通过；
`any`、`symbol`、原型链改写、`eval`、`with`、条件类型、映射类型全部不通过。

## 五、类型集

### 5.1 机器类型（新增）

| 类型 | 宽度 | 语义 |
|---|---|---|
| `i8` `i16` `i32` `i64` | 1/2/4/8 字节有符号 | 二进制补码，溢出**回绕** |
| `u8` `u16` `u32` `u64` | 1/2/4/8 字节无符号 | 溢出**回绕** |
| `f32` | 4 字节 | IEEE-754 单精度 |
| `f64` | 8 字节 | IEEE-754 双精度 |
| `bool` | 1 字节（内部按 `i32` 处理） | 仅 `true` / `false` |
| `char` | 4 字节 | Unicode 码位 |
| `usize` `isize` | 指针宽度 | 索引与长度 |

### 5.2 与既有类型的关系

- `number` **保持** TypeScript 语义，永远映射到 `f64`，不得改动。
- `boolean` 与 `bool` 是两个类型：前者是 TS 的，后者是机器类型；静态区底层表示一致（`i32`），类型上不互通。
- `string` 表示为 `GcRef<Str>`（UTF-16，与 JS 一致，避免边界转换损耗）。
- `interface` 在静态区为**扁平布局的值类型**（区别于 TS 的结构类型惯例，此为 mio 扩展语义）。

### 5.3 明确不支持

`any`、`unknown`、`symbol`、条件类型、映射类型、模板字面量类型、原型链改写、`eval`、`with`、隐式 `this` 绑定。
使用即编译期报错，并提示替代写法。

## 六、表示决策表

核心机制一句话：

> 每一个类型，在编译期必须被判定为「一种确定的内存表示」；凡是判不出来的，一律编译期报错。

### 6.1 两类表示

所有类型先归入两类之一，这是内存管理的地基：

| 类别 | 含义 | 能否栈上/静态分配 | 谁负责释放 |
|---|---|---|---|
| **POD** | 纯值，不含指针 | ✅ | 不需要（随栈帧消亡） |
| **GcRef** | 指向堆对象的引用 | ❌ | GC |

### 6.2 决策表

| 类型 | 表示 | 类别 |
|---|---|---|
| `i8..i64` / `u8..u64` | `I8..I64` / `U8..U64` | POD |
| `f32` / `f64` / `number` | `F32` / `F64` | POD |
| `bool` / `boolean` | `I32`（0/1） | POD |
| `char` | `I32`（码位） | POD |
| `struct`（字段全为 POD） | 扁平布局，按字段宽度内联 | POD |
| `struct`（含 `GcRef` 字段） | 扁平布局 + 内联引用 | GcRef（需栈映射） |
| `enum`（代数数据类型） | tag + payload，payload 宽度取最大变体 | 按变体 |
| `T[]`（`T` 已定） | `GcRef<Array<T>>`，槽位宽度 = `sizeof(T)` | GcRef |
| `string` | `GcRef<Str>` | GcRef |
| `class` | `GcRef<ClassInst>` | GcRef |
| `T` 未特化 | **编译期报错** | — |

### 6.3 收益

区分 POD 并非仅为将来可能的无 GC 模式，它直接带来性能：

- `struct` 可全栈上，无指针追逐
- 数组元素可内联（`i32[]` 槽位 4 字节，不是 8 字节指针 + 解引用）
- 逃逸分析失败时的分配可降到最小

## 七、数值语义

### 7.1 运算

- 算术分派取决于**静态类型**，不做运行时探测。
- `i32 + i32` → 32 位加法，溢出**回绕**（对齐 AS/C 的有符号实现），不 panic、不是 UB。
- `f32` 与 `f64` 之间**不隐式提升**；`f32 + f64` 是编译期错误。
- `i32 + f64` 是编译期错误，必须显式转换。
- 整数除法为**截断除法**（向零取整）；除零在运行期为**明确定义的错误**（不返回 `Infinity`）。
- `%` 对整数为取余，符号随被除数。

### 7.2 字面量

- 无标注整数字面量按上下文推断；推断不出时默认 `i32`（超范围则 `i64`）。
- `1.0` 为 `f64` 字面量；无后缀形式。
- 字面量超范围为编译期错误，不静默截断。

### 7.3 转换

仅三种形式，全部**显式**：

| 形式 | 语义 |
|---|---|
| `T(x)` | 显式数值转换，语义按目标类型逐一定义 |
| `i32.trunc/f64.wrap/...` | 收窄转换必须指名语义，见 7.4 |
| 边界转换 | 与宿主 / 外部 ABI 交互，唯一允许装箱的位置 |
| `unsafeCast<T>(x)` | 位重解释，绕过一切检查，见第八节 |

不存在隐式转换。这是「强类型」在数值层的体现。

### 7.4 收窄转换

收窄（如 `i64 → i32`、`f64 → i32`）必须**显式指名语义**，不提供默认行为：

| 形式 | 语义 |
|---|---|
| `trunc32(x)` | 截断：丢弃高位（对齐 C 的整数转换） |
| `wrap32(x)` | 回绕：保留低位，按目标宽度回绕 |
| `sat32(x)` | 饱和：超出范围时钳到 `MIN`/`MAX` |
| `f64ToI32(x)` | 浮点转整数：向零取整，超范围时为**运行期明确定义的错误** |

`as` **不允许**用于收窄。理由：收窄语义选错是金额计算与协议解析的经典 bug 源，不能有「默认行为」可言。

## 八、健全性与类型断言

### 8.1 问题

TypeScript 的类型系统是**不健全**的：`as` 一个断言就能把任何值变成任何类型。
若不加约束，「静态强类型」就只是装饰品。

### 8.2 三级规则

| 级 | 写法 | 允许的转换 | 检查 |
|---|---|---|---|
| 一 | `as` | 仅**可证明安全**的转换：数值扩宽（`i32 → i64`、`f32 → f64`）、`T → T \| null`、已收窄联合的字面量、引用类型向下转型 | 编译期证明；引用类型转型额外做运行时 `typeid` 检查 |
| 二 | `unsafeCast<T>(x)` | 任意表示转换（位重解释） | 不检查，但**记录在案**；`--deny-unsafe` 可全量拒绝 |
| 三 | 编译期报错 | 跨表示断言（`string as i32`）、数值收窄（`i64 as i32`，须按 7.4 指名语义）、以 `any`/`unknown` 为起点 | — |

### 8.3 逃生舱为何用函数而非运算符

`unsafe as` 这种拼写**不是合法 TypeScript 语法**——TS 的 `as` 表达式形式固定为 `expr as Type`，中间插不进关键字。若为此新增语法，违反「语法零改动」总纲。

因此逃生舱采用**内置泛型函数**：

```ts
declare function unsafeCast<T>(value: unknown): T;
```

```ts
const bits: i32 = unsafeCast<i32>(someFloat);
```

收益：

1. **合法 TS**：普通泛型函数调用，parser 无需改动，符合总纲。
2. **可 grep**：`grep -r unsafeCast` 一次列全。
3. **可移除**：`--deny-unsafe` 直接将该内置函数从作用域移除，使用即编译错误，比 lint 更难绕过。
4. **名字自解释**：读代码即知此处放弃检查。

### 8.4 引用类型向下转型

`(T)x` 式的引用类型转型必须做**运行时检查**，失败为明确定义的错误（不制造 UB）。为此每个 `class` 实例携带 **typeid**（8 字节）。

代价：每实例 +8 字节，每次转型一次比较。接受此成本，理由是健全性不能在引用类型上开洞。
若后续引入类型层次的真实需求，可再评估「限制类继承（单层或禁止）」以把多数转型静态解析。

### 8.5 配套要求

- `--deny-unsafe`：安全关键项目的推荐开关。移除 `unsafeCast` 内置声明，同时禁止 `--no-bounds-check`。
- `mio check --audit`：输出全部 `unsafeCast` 使用点清单，供代码审计。
- 不对 `any` 提供任何通道，因此不存在「绕过检查」的路径。

### 8.6 与 AssemblyScript 的分化

AssemblyScript 提供 `changetype<T>()`（无标记的位重解释）与 `unchecked()`（无法关闭的边界检查豁免）——两个都是无开关的后门。

mio 的对照：`unsafeCast<T>()` 名字自带警示、可 grep、可整体移除。这是双方最实质的分化点。

## 九、安全承诺四件事

这是「静态强类型」的兑现清单，也是面向高安全等级场景的唯一正确宣传口径。

### 9.1 健全性（Soundness）

见第八节。核心承诺：**通过编译且未使用 `unsafeCast` 的程序，不存在类型混淆。**

### 9.2 无未定义行为（No UB）

| 情形 | 处理 |
|---|---|
| 数组越界 | 运行期检查 + 明确报错；`--no-bounds-check` 供信任代码，由 `--deny-unsafe` 一并禁止 |
| 整数溢出 | 已定为回绕，定义良好，非 UB |
| 未初始化变量 | 编译期拒绝 |
| 空引用 | 由 `T \| null` + 控制流收窄排除，非空类型不可能为 `null` |
| 悬垂引用 | 由 GC 排除（无手动 `free`） |
| 除零 | 运行期明确定义的错误 |
| 转型失败 | 运行期明确定义的错误（对齐 C# 的 `InvalidCastException`），非 UB |
| 数据竞争 | 单线程模型下不存在；引入并发时需另立规则 |

### 9.3 确定性

- 分配时机与大小应可静态分析：逃逸分析成功即栈上分配（阶段 2）
- GC 停顿可观测、可限制：堆上限可配置，回收策略可观测
- 不做「看心情触发」的优化；同一输入在同一编译配置下产出同一结果

### 9.4 可审计

- 无 `eval`、无动态 `import`、无运行时反射
- 无 `node_modules`（立项时已定，此处为安全收益）
- 运行时足够小，可人工通读（小 TCB）
- `unsafeCast` 使用点可枚举、可导出清单

### 9.5 边界澄清

「静态强类型」不等于「安全认证」。金融与军工的合规要求涉及认证流程（如 DO-178C、MISRA）、形式验证与组织流程，非语言层面可单独满足。

正确的对外口径是：

> **TS 语法 + 静态类型 + 原生性能 + 内存安全** —— 一个比 Go 严格、比 Rust 好学的高性能语言。

不是「军工级」。前者经得起验证，后者经不起。

## 十、值语义与引用语义

| | 值语义 | 引用语义 |
|---|---|---|
| 关键字 | `struct` / `interface` / 机器类型 / `enum` | `class` / 数组 / `string` |
| 赋值 | 逐字节拷贝 | 拷贝指针 |
| 相等 | 逐字段比较（`==` 可用） | 指针比较（`===` 语义） |
| 栈上 | 可以（POD） | 不可以（永远在堆） |
| 作为参数 | 默认按值；`in`/`ref` 可改 | 传引用 |

规则：

1. `class` 保留 TS 的引用语义，不做改动。
2. `struct` 与 `interface` 为**值类型**：赋值拷贝、可栈上、不可为 `null`。
3. 值类型字段只能是值类型或 `GcRef`。
4. 值类型不允许自引用（否则宽度无穷），需要自引用时改用 `class`。

## 十一、可空性

对齐 Rust 的 `Option<T>` 而不是 Java 的 `null`：

- 值类型不可为 `null`（无此值）。
- 引用类型默认**非空**；可空须写成 `T | null`，访问前必须收窄。
- 收窄沿用 TS 的控制流收窄，静态区实现为**一次运行时判空 + 后续路径免判**。

理由：`null` 是 Java 最大的历史包袱，静态运行时有能力在类型层消掉它，就不该重造。

---

## 十二、内存管理

### 12.1 路线决策

| 路线 | 结论 |
|---|---|
| **GC（采用）** | 与 TS 用户心智一致；边界转换简单；运行时复杂度换生态与可用性 |
| 手动 `free` | 否决。安全性压在人的记忆上，TS 用户无内存经验 |
| 所有权 / 借用检查 | 否决。需后端围绕生命周期整体设计，与阶段 0 冲突；学习成本最高 |

### 12.2 分阶段方案

| 阶段 | 方案 | 升级触发条件 |
|---|---|---|
| 0~1 | **bump allocator**（线性分配，永不回收；进程退出由 OS 统一回收） | 短命进程足够，分配成本为一次加法 |
| 2 起 | **精确 mark-sweep**（stop-the-world + 栈映射） | 需要 REPL、长驻进程、`serve()` 时，泄漏会累积 |
| 4 | **分代 GC**（young gen 用 bump + minor GC） | 分配密集场景出现瓶颈时 |

### 12.3 明确不采用

- **引用计数**：每次写指针都要维护计数，热路径开销明确；循环引用无法回收，需额外弱引用机制。GC 下这是非问题。
- **并发 / 增量 GC（早期）**：需读写屏障与三色标记的正确性论证，是隐蔽 bug 的高发区。stop-the-world 在阶段 2 足够。

## 十三、性能定位

> **目标：接近 C，优于 Go。不是 Rust 档。**

| 场景 | vs C | 对比 Go |
|---|---|---|
| 数值热循环 | 1.0~1.3x | **略快**（Go 有接口装箱与边界检查，静态区没有） |
| 字符串 / 数组密集 | 1.5~3x | **略慢**（Go 的 GC 更成熟，且有逃逸分析） |
| 尾延迟（p99） | 差 | **明显更差**（stop-the-world mark-sweep vs Go 的并发 GC） |
| 启动时间 | 优 | 优（无 JIT 预热） |
| 内存占用 | 优 | 优（无 JIT 代码缓存） |

Cranelift 相对 LLVM 的差距体现在优化质量上：数值代码可达 -O1~-O2 水平，不是 -O3。若后期性能不足，可换 LLVM 后端——IR 不变，只换 codegen。

## 十四、分阶段路线

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **0** | `i32`/`i64`/`f32`/`f64` + 局部变量 + 函数 + `if`/`while`/`for` + 定长数组 + `string`；Cranelift codegen；bump allocator；产出**原生可执行文件** | `fib(40)` 比 Node 快 5~10x，接近 C；不依赖任何 JS 运行时 |
| **1** | `struct` / `enum` + `match` + `T \| null`；健全性检查（第八节） | 能写 tokenizer，`--deny-unsafe` 通过 |
| **2** | 泛型单态化；逃逸分析（能栈上的不上堆） | 泛型容器零装箱 |
| **3** | 精确 mark-sweep GC；`@std/*` 原生接入 | 长驻服务可跑，内存不无界增长 |
| **4** | 分代 GC；可选 wasm 后端；可选 Boa 互操作 | — |

阶段 0 的产物即为真正的原生可执行文件，不依赖 JS。这一步做成，核心命题即已验证。

## 十五、非目标

明确不做，防止反复纠结：

- **无 GC 模式 / 静态分配全程序**：不做。GC 是既定路线。
- **嵌入式（MCU / RTOS / 裸机）**：不做。需 `no_std`、无分配器、中断与 MMIO，与托管运行时形态互斥。
- **所有权 / 借用检查**：不做。见 12.1。
- **Node.js / CommonJS / `node_modules` 兼容**：不做。立项时已定。
- **wasm 作为性能主路径**：不做。wasm 仅为可选第二目标。
- **JIT**：不做。Cranelift AOT 的编译速度已足够，JIT 需处理 deopt，复杂度不成比例。
